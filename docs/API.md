# API standard

The rules for the agent-hub HTTP API. The decision is [ADR 0004](adr/0004-rest-api-standard.md).

**Status: implemented in Phase 2**, in `packages/api` (`agent_hub.api`, FastAPI), served by `hub web` together with the
web app in `apps/web` (React). Every rule below is in force; the Phase 2 additions (versioning, methods, committed
contract, error mapping, pagination, SSE, local security) were the "proposed defaults" of this document, confirmed when
the first routes were written ([ADR 0017](adr/0017-api-second-composition-root.md)).

## Style and naming

- Resource-oriented REST. Resources are nouns, not actions: `GET /api/v1/sessions`, not `GET /api/v1/getSessions`.
- Every route is under the `/api/v1` prefix.
- Collection names are plural kebab-case nouns: `/api/v1/projects`, `/api/v1/sessions/{session_id}`,
  `/api/v1/workflow-runs`.
- Names follow the SPEC glossary ([CONVENTIONS.md](CONVENTIONS.md)): a Session is never a "run", "job" or "execution".

## Contract

- The OpenAPI document that FastAPI generates from the routes and their Pydantic models is the contract. There is no
  hand-written spec.
- The web TypeScript client is generated from that OpenAPI document; nobody writes client types by hand.
- Both are committed: `packages/api/openapi.json` (exported by `scripts/export_openapi.py`) and
  `apps/web/src/api/schema.d.ts` (generated by `openapi-typescript`; the client is `openapi-fetch`). `make openapi`
  regenerates them; `make check-fast` (`openapi-check`) fails when either is stale, so a contract change shows in review.
- The document lists only routes this build serves: no route for a later phase exists in it.

## Payloads

- JSON fields are `snake_case`, in requests and responses.
- Timestamps are ISO 8601 strings in UTC with an explicit offset: `"2026-09-27T14:03:12Z"`.
- Ids the platform mints are UUIDv7 strings, generated with `uuid.uuid7()` (stdlib since Python 3.14): a stored event's
  `event_id` and a registered hub's id. Entities keep their sources' ids: a Session is its Claude Code session id, a
  WorkflowRun its `hub run` id, a project its `project.name`.
- Money is a decimal string with four places (`"1.2500"`); a derived value carries `derived: true`, and a value whose
  source is not connected is `null` with that source in `sources_missing`.
- Request and response bodies are Pydantic models in `core` or in the API package; no bare dicts.

## Errors

Errors are RFC 9457 Problem Details, with media type `application/problem+json`:

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "No session with id 01923f1e-7c4a-7d2e-9b1a-3c5d8e2f4a6b.",
  "instance": "/api/v1/sessions/01923f1e-7c4a-7d2e-9b1a-3c5d8e2f4a6b"
}
```

- `type` is `about:blank` (the RFC 9457 default, meaning the problem is just the HTTP status, with `title` its reason
  phrase) until a specific problem type is defined; `detail` is specific to this occurrence.
- Each named domain exception maps to one problem in one place, `agent_hub/api/rfc9457.py`: unknown id → 404 naming
  the id; a bad parameter or cursor → 400 with `errors[]` naming the parameter; an invalid body → 422; a body over
  1 MiB → 413; an unregistrable hub → 422 ("No hub.json", "Invalid hub.json" with JSON-pointer `errors[]`); a
  project registered twice → 409; an event conflict → 409; a busy or unreadable database or hub registry → 503.
  Anything else is a generic 500 problem; the server logs it as structured JSON without payload strings, so neither
  the answer nor the log holds a secret or a traceback.

## Pagination

Lists use cursor pagination: the client pages through a collection with an opaque cursor, never an offset (offsets skip
or repeat items while sessions are being written). `GET /api/v1/sessions?limit=50&cursor=<opaque>` returns
`{"items": [...], "next_cursor": "<opaque>", "total_estimate": N}`; `next_cursor` is `null` on the last page. `limit` is
1 to 200 (default 50), a cursor at most 512 characters, `q` at most 200. A cursor carries the store's high-water mark of
its first page, so later pages fold only the events up to it and an append between pages never repeats or skips an
item.

## Live updates

Live sessions stream over Server-Sent Events (SSE). SSE is one-way; actions (approve a gate, start a workflow) are
ordinary HTTP requests. Streams: `GET /api/v1/events/stream` (global: `counts`, `collector`, `tile.*`, …),
`/live-sessions/stream`, `/sessions/{session_id}/events/stream` and `/workflow-runs/{run_id}/stream`, with
`Accept: text/event-stream`.

- On connect the server sends `retry: 3000`. Every message that carries a stored event has that event's `event_id` as
  its SSE `id`; a heartbeat every 15 s carries the last real id.
- A client reconnecting with `Last-Event-ID` gets the events after it replayed in append order, up to 10,000 events or
  24 hours; past that, or for an unknown id, it gets `event: reset` and reloads.
- The server polls the store's high-water mark every 500 ms, so events appended by other processes (`hub collect`,
  `hub run`) reach the streams.

## Thin routes

A route does three things and nothing else:

1. validate the request (FastAPI and the Pydantic models do this);
2. call ONE core use case, with the adapters it needs;
3. map the use case's result, or its domain exception, to the response.

No business logic, queries or tracker calls in a route. The CLI, the API and the collector call the same use cases, so
the same operation behaves the same from every entry point ([ARCHITECTURE.md](ARCHITECTURE.md)).

## Versioning and methods

- A breaking change goes to a new version prefix (`/api/v2`); `v1` keeps working until it is retired.
- Nested paths only for ownership (`/api/v1/sessions/{session_id}/events`). Methods keep their HTTP meaning: `GET`
  reads, `POST` creates or triggers an action (`POST /api/v1/hubs`, `POST /api/v1/events/hooks`), `PATCH` updates part
  of a resource, `DELETE` removes it. In Phase 2 the only writes are registering and removing a hub and posting hook
  envelopes.

## Local security

`hub web` binds `127.0.0.1` only. It refuses a `Host` header other than `127.0.0.1:<port>`, `localhost:<port>` or
`[::1]:<port>` (403, against DNS rebinding) and a `POST` or `DELETE` whose `Origin` is not its own (403); it sends no
CORS headers, `Cache-Control: no-store` on `/api`, and a CSP that limits scripts, styles, fonts and connections to
`'self'`. The web app requests no other host.
