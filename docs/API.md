# API standard

The rules for the agent-hub HTTP API. The decision is [ADR 0004](adr/0004-rest-api-standard.md).

**Status: implemented in Phase 2**, in `packages/api` (`agent_hub.api`, FastAPI), served by `hub web` together with the
web app in `apps/web` (React). Every rule below is in force; the Phase 2 additions (versioning, methods, committed
contract, error mapping, pagination, SSE, local security) were the "proposed defaults" of this document, confirmed when
the first routes were written ([ADR 0017](adr/0017-api-second-composition-root.md)).

## Style and naming

- Resource-oriented REST. Resources are nouns, not actions: `GET /api/v1/sessions`, not `GET /api/v1/getSessions`.
- Every route is under the `/api/v1` prefix.
- Collection names are plural kebab-case nouns: `/api/v1/projects`, `/api/v1/sessions/{session_id}`,
  `/api/v1/workflow-runs`.
- Names follow the SPEC glossary ([CONVENTIONS.md](CONVENTIONS.md)): a Session is never a "run", "job" or "execution".

## Contract

- The OpenAPI document that FastAPI generates from the routes and their Pydantic models is the contract. There is no
  hand-written spec.
- The web TypeScript client is generated from that OpenAPI document; nobody writes client types by hand.
- Both are committed: `packages/api/openapi.json` (exported by `scripts/export_openapi.py`) and
  `apps/web/src/api/schema.d.ts` (generated by `openapi-typescript`; the client is `openapi-fetch`). `make openapi`
  regenerates them; `make check-fast` (`openapi-check`) fails when either is stale, so a contract change shows in review.
- The document lists only routes this build serves: no route for a later phase exists in it. Its paths are Phase 2's
  (`P2_PATHS` in `agent_hub/api/openapi_paths.py`) plus the five AGH-201 added (`CLARITY_PATHS`):
  `GET /sessions/{session_id}/problems`, `POST /learnings/{learning_id}/accept`, `POST /learnings/{learning_id}/reject`,
  `GET /projects/{project}/brain` and `GET /projects/{project}/brain/note?path=…`, and the one AGH-136 added
  (`TICKET_PATHS`): `GET /features/{project}/{slug}/tickets` ([Feature tickets](#feature-tickets)), and the three
  AGH-164 added (`SKILL_PATHS`, all GET): `/projects/{project}/skills`, `/projects/{project}/skills/{kind}/{source}/{name}`

## Payloads

- JSON fields are `snake_case`, in requests and responses.
- Timestamps are ISO 8601 strings in UTC with an explicit offset: `"2026-09-27T14:03:12Z"`.
- Ids the platform mints are UUIDv7 strings, generated with `uuid.uuid7()` (stdlib since Python 3.14): a stored event's
  `event_id` and a registered hub's id. Entities keep their sources' ids: a Session is its Claude Code session id, a
  WorkflowRun its `hub run` id, a project its `project.name`.
- Money is a decimal string with four places (`"1.2500"`); a derived value carries `derived: true`, and a value whose
  source is not connected is `null` with that source in `sources_missing`.
- Request and response bodies are Pydantic models in `core` or in the API package; no bare dicts.

## Errors

Errors are RFC 9457 Problem Details, with media type `application/problem+json`:

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "No session with id 01923f1e-7c4a-7d2e-9b1a-3c5d8e2f4a6b.",
  "instance": "/api/v1/sessions/01923f1e-7c4a-7d2e-9b1a-3c5d8e2f4a6b"
}
```

- `type` is `about:blank` (the RFC 9457 default, meaning the problem is just the HTTP status, with `title` its reason
  phrase) until a specific problem type is defined; `detail` is specific to this occurrence.
- Each named domain exception maps to one problem in one place, `agent_hub/api/rfc9457.py`: unknown id → 404 naming
  the id; a bad parameter or cursor → 400 with `errors[]` naming the parameter; an invalid body → 422; a body over
  1 MiB → 413 (160 MiB for `POST /api/v1/agent-sessions` and
  `POST /api/v1/agent-sessions/{id}/messages`, which may carry images and files); an unregistrable hub → 422 ("No hub.json", "Invalid hub.json" with JSON-pointer `errors[]`); a
  project registered twice → 409; an event conflict → 409; a busy or unreadable database or hub registry → 503.
  Anything else is a generic 500 problem; the server logs it as structured JSON without payload strings, so neither
  the answer nor the log holds a secret or a traceback.
- The brain routes: a path the brain rules refuse (`..`, absolute, too long, too deep, not `.md`) → 400 "Invalid brain
  path" with `errors[]` naming `path`; a missing note, a link, a path under `auto/` or a file that is not regular →
  one 404 "Brain note not found" (existence is not revealed); a note over 256 KiB → 413 "Brain note too large".
- The knowledge routes ([Knowledge](#knowledge)): a `q` with no word → 400 naming `q`; a backlinks `path` → the brain
  routes' 400 and 404 above; the hub's checkout that cannot be listed → 502 "Could not read the hub's files"; SQLite
  without FTS5 → 503 "Search unavailable"; the index's database that cannot be upgraded → 503 "Database upgrade
  failed". `GET /learnings`'s `brain_path` outside the brain → 400 naming it.
- The learning decisions ([Learning decisions](#learning-decisions)): every refusal is a 409 whose extension members
  `code` and `reason` say why, nothing pushed or stored. `code` is `learning_conflict` (already decided, with
  `pr_url` when its PR is known; another action running for the hub; no reason to reject; a target the brain rules
  refuse), `change_request_conflict` (the note is neither on `origin/<default branch>` nor in the hub checkout
  ([ADR 0037](adr/0037-learning-decisions-unpushed-notes-and-edits.md)), the destination or the branch
  exists, `origin` is not the hub repo), `push_refused` (the push guard refused the branch) or `hub_read_only`
  (actions unavailable for this hub, title "Learning actions unavailable", the same reason the learning's
  `actions_unavailable` shows). A git or `gh` step that fails → 502 "Could not open the pull request" with the
  member `step` (`clone`, `read`, `branch`, `commit`, `push`, `pr`, …) and never the tools' output; the 60 s deadline
  → 504 "Could not open the pull request in time". A body that is not JSON → 415 (Local security). The routes answer
  501 only in a build where the decisions are not wired.
- The feature tickets route ([Feature tickets](#feature-tickets)) never answers an error for a failed Linear read:
  the failure is the `tracker_problem` member of its 200 answer.
- The agent-session routes ([Agent sessions](#agent-sessions)) answer typed problems,
  `urn:agent-hub:problem:agent-session-<code>`, listed there.
- The skills routes ([Skills](#skills)): a `kind` other than `skill`, `agent` or `hook`, a `source` or `name` outside
  `[A-Za-z0-9_-]{1,128}` or a `file_id` that is not 16 hex characters → 400 "Invalid request parameter" naming it,
  before any file is read; an unknown project, an item the catalog does not hold or a file id its detail did not
  issue → 404 (entity `project`, `skill` or `skill file`); a bundled file over 256 KiB → 413 "Skill file too large".
  The version history routes (Skills and Workflows) answer the same 400s, and 400 for a `version_id` that is not a
  lowercase UUID, before anything is read; an item with no unit (a link, a built-in) → 404 (entity `item history`); a
  version id of another unit, or unknown → 404 (entity `item version`). No problem names a path.
- The restores ([Skills](#skills), [Workflows](#workflows)) and the Publish ([Skills](#skills)): a refusal is a 409
  "Item write refused" whose extension members `code` and `reason` say why, nothing written and no `restore` or
  `publish` version recorded: `hub_read_only` (the hub
  folder is not writable, and always in the container, before the cookie is checked), `no_author` (the hub has no
  effective identity; `reason` says what is missing), `link_in_path` (a component of the unit's path is a link),
  `unit_unreadable` (the unit on disk cannot be read whole, so it could not be recorded first),
  `secret_unversioned` (the unit on disk has a secret match) or `managed_confirmation_required` (`hub.lock` manages
  the unit and the body did not say `confirm_managed: true`; only the JSON `true` confirms, `1` or `"yes"` is a
  422). A Publish also refuses `draft_already_published` ("This draft was already published; discard it": a
  version of the project already names the draft as its `publish`; it answers before any not-found, invalid-draft or
  draft-read refusal; nothing is written, recorded or removed and the draft stays), `item_exists` (a new item, or a
  rename, to a name its kind already has in any source, case aside; a new hook's script path holding other bytes; a
  moved hook whose groups the file already holds) and `link_in_path` for a draft file or folder that is a link or a
  special file; `unit_unreadable` also when the draft must merge into a unit past the bounds. The disk's content may already be recorded as an
  `external` version when a managed refusal answers. A body field the model does not know → 422. A write that fails →
  500 "Item write failed", `code` `write_failed` and `kind` `failed` (the unit is as it was), `rollback_failed` (a
  folder swap could not put the old folder back; `hub doctor`'s `items.leftovers` lists what is left beside it) or
  `old_not_removed` (a Publish's rename: the new item is published, its old item could not be removed and stays
  until the user removes it, and so does the draft; the body also carries `published: true` and the write's
  `changed`, `versioned` and `reason`, and the detail reads "Published; the old item could not be removed and
  stays. The draft is still there: discard it.", since a recorded `publish` spends it); a stored version that does not decode → 500 `corrupt_version`. A race for the unit's next version lost three times
  → 503 with `Retry-After: 1` and `written`: `false` with `code` `version_race` when nothing was written yet, `true`
  with `code` `written_not_recorded` when the unit was written but its version not stored (the race lost, or the
  database busy or unreadable, after the write; the next read records it as `external`). No problem names a path.
- The Publish ([Skills](#skills)) also answers, before anything is written or recorded: 400 for a `draft_id` outside
  `(skill|agent|hook)-[a-z0-9]{6}`; 422 for a body outside its shape (a `target` field or `kind` outside the catalog's,
  an unknown field, `confirm_managed` other than a JSON boolean), before anything is read; 404 for an unknown project
  or target item (entity `project`, `skill` or the unit's kind) and a missing or empty draft folder (entity `draft`);
  413 "Draft too large" (`code` `draft_too_large`, `limit` the bounds in words) for a draft with a file over 256 KiB,
  more than 201 files or deeper than 3; 422 "Draft invalid" (`code` `draft_invalid`, `reason` in words) for a draft
  whose main file is missing (`SKILL.md`, one agent `.md`, `hooks.json`), whose frontmatter `name` is outside
  `[A-Za-z0-9_-]{1,128}`, whose kind (its id's prefix) differs from the target's, whose `hooks.json` is not a hooks
  object, that holds a hidden name, or that edits a hook and carries scripts. A Publish that wrote the item but could
  not remove the draft answers 500 "Draft not removed" (`code` `draft_not_removed`, `published: true`, and the
  write's `changed`, `versioned` and `reason`; detail "Published; the draft is still there. Discard it."): the item
  stays published and the kept draft is spent when a `publish` was recorded. A draft that cannot be read (an I/O
  error, not a link or the bounds) answers 500 "Draft read failed" (`code` `write_failed`, `kind`
  `draft_unreadable`; detail "The draft could not be read; nothing was written or recorded.").

## Pagination

Lists use cursor pagination: the client pages through a collection with an opaque cursor, never an offset (offsets skip
or repeat items while sessions are being written). `GET /api/v1/sessions?limit=50&cursor=<opaque>` returns
`{"items": [...], "next_cursor": "<opaque>", "total_estimate": N}`; `next_cursor` is `null` on the last page. `limit` is
1 to 200 (default 50), and for a session's events (`GET /api/v1/sessions/{session_id}/events`) 1 to 1,000 (default
200), which its detail page reads whole; a cursor is at most 512 characters, `q` at most 200. A cursor carries the store's high-water mark of
its first page, so later pages fold only the events up to it and an append between pages never repeats or skips an
item.

## Live updates

Live sessions stream over Server-Sent Events (SSE). SSE is one-way; actions (approve a gate, start a workflow) are
ordinary HTTP requests. Streams: `GET /api/v1/events/stream` (global: `counts`, `collector`, `tile.*`, …),
`/live-sessions/stream`, `/sessions/{session_id}/events/stream` and `/workflow-runs/{run_id}/stream`, with
`Accept: text/event-stream`.

- On connect the server sends `retry: 3000`. Every message that carries a stored event has that event's `event_id` as
  its SSE `id`; a heartbeat every 15 s carries the last real id.
- A client reconnecting with `Last-Event-ID` gets the events after it replayed in append order, up to 10,000 events or
  24 hours; past that, or for an unknown id, it gets `event: reset` and reloads.
- The server polls the store's high-water mark every 500 ms, so events appended by other processes (`hub collect`,
  `hub run`) reach the streams.

## Thin routes

A route does three things and nothing else:

1. validate the request (FastAPI and the Pydantic models do this);
2. call ONE core use case, with the adapters it needs;
3. map the use case's result, or its domain exception, to the response.

No business logic, queries or tracker calls in a route. The CLI, the API and the collector call the same use cases, so
the same operation behaves the same from every entry point ([ARCHITECTURE.md](ARCHITECTURE.md)).

## Versioning and methods

- A breaking change goes to a new version prefix (`/api/v2`); `v1` keeps working until it is retired.
- Nested paths only for ownership (`/api/v1/sessions/{session_id}/events`). Methods keep their HTTP meaning: `GET`
  reads, `POST` creates or triggers an action (`POST /api/v1/hubs`, `POST /api/v1/events/hooks`), `PATCH` updates part
  of a resource, `DELETE` removes it. The only writes are registering and removing a hub, posting hook envelopes,
  since AGH-201 the two learning decisions, since AGH-165 the agent-session commands, since AGH-297 the restore
  of an item's version, the first route that writes into a hub's working tree, and since AGH-298 the Studio's Publish
  of a draft (see Skills). Since AGH-296 the
  Toolkit and Workflows `GET`s also record item versions in agent-hub's database (never in the hub, see Skills), and
  since AGH-393 the knowledge `GET`s sync the knowledge index's derived rows first (see Knowledge).

## Sessions

`GET /api/v1/sessions` and `GET /api/v1/sessions/{session_id}` carry, besides the folded counts, the fields a Live tile
shows, derived on read by the same code as `GET /api/v1/live-sessions` (never stored, no new payload key). They are
filled for the rows of the page only; every one is optional and `null` when there is nothing to say.

| Field | Value |
| --- | --- |
| `waiting_reason` | why a `waiting` session waits (`Guard ask`, `Plan approval`, `Spec approval`, `Human gate`, `Permission prompt`); a `live` or `idle` session whose driven agent session waits on a permission request reads `Permission prompt`, as its Live tile does, and keeps its `status` |
| `last_action` · `last_tool` | the last tool call in plain words (`Ran make check`, `Edited src/app.py`) and its tool |
| `needs_you_problem` | the "what went wrong" line of the first problem that needs the owner |
| `failing_notice` | the same gate or command failed 2 times in a row, or 3 tool errors in the last 5 minutes |
| `sparkline_60s` | an empty list while the session has not ended (the web fills it from the event stream); `null` once it has ended |

## Learning decisions

`POST /api/v1/learnings/{learning_id}/accept` with `{"target": "<folder or .md path under brain/>"}` (1 to 200
characters) and an optional `"note_body"` (the note's text after its frontmatter as the owner edited it, 1 to 262,144
characters, an empty one is 422; a blank one or one over 256 KiB of UTF-8 is a 409 `learning_conflict`; [ADR 0037](adr/0037-learning-decisions-unpushed-notes-and-edits.md)),
and `POST /api/v1/learnings/{learning_id}/reject` with `{"reason": "…"}` (1 to 300 characters once
stripped; an empty one is 422) each open one pull request in the hub repo and answer 201 with
`{"state": "accepted_pr_open" | "rejected_pr_open", "pr_url": "https://github.com/<hub_repo>/pull/<n>", "branch": "…"}`.
They are actions, not resources, a deliberate exception to "resources are nouns"
([ADR 0024](adr/0024-learning-actions-from-the-app.md)).

- Nothing is written to the default branch or to the user's checkout: the change is one commit on a new branch of a
  temporary clone, pushed without force, and the PR waits for the user to merge it.
- **Branch name exception.** The branch is `<branch_prefix>learning-<accept|reject>-<note slug>` (e.g.
  `roquettejh/learning-accept-testing-x`): a learning has no tracker issue, so the `<team>-<n>-<desc>` rule of
  [CONTRIBUTING.md](CONTRIBUTING.md) does not apply to these branches only. The push guard refuses any other name.
- The PR title is `Accept learning: <title>` or `Reject learning: <title>` (redacted, at most 72 characters); its body
  names the move, says when the note was edited in agent-hub, quotes the note's first paragraph (the edited one when
  there is an edit; redacted, 200) and, for a reject, the reason. An edited accept writes the new body after the kept
  frontmatter in the same commit. The commit is
  authored as the hub's author (ADR 0016) with no trailer.
- A decision is idempotent by the learning's state: a second call answers 409 with the PR already open.

## Knowledge

Two `GET` routes (`KNOWLEDGE_PATHS`, AGH-393) read a project's hub through the knowledge index that `hub search` and
`hub mcp` use ([ADR 0044](adr/0044-team-memory-git-source-local-index-and-hub-mcp.md)). Each first syncs the index
with the checkout of the project's registered hub (`git ls-files` of its `brain/` and of each repo's `docs/`; only new
or changed files are read), then answers. The rows are keyed by the registered hub's path, so a hub registered at its
main checkout shares its rows with `hub search`. Neither route writes the hub or a repo.

- `GET /api/v1/projects/{project}/knowledge/search?q=&kind=&limit=` → `KnowledgeSearch`: `project`, `query`,
  `results` (each `path`, `kind`, `title`, `status`, `provenance`, a one-line plain-text `snippet`), `sync` (`listed`,
  `read`, `indexed`, `dropped`), `skipped` (`path`, `reason`) and `warnings`, one per repo that is not checked out
  (`<dir>: not checked out; its docs are not searched`). `q` is 1 to 500 characters and only its runs of letters and
  digits are searched, all required, never as FTS5 syntax; `kind` repeats, at most 10, each one of the index's kinds;
  `limit` is 1 to 50, default 50. Results come best first, as `hub search` prints them; none is `results: []`.
- `GET /api/v1/projects/{project}/brain/backlinks?path=` → `NoteBacklinks`: `project`, `path`, `items` (each
  indexed document holding a Markdown link to `brain/<path>`: `path`, `kind`, `title`), sorted by path, at most 100,
  and `total`, the full count. `path` is checked exactly as `GET …/brain/note` checks it, before anything is read. The
  note need not exist: a dead link still lists its sources. Only links into `brain/` are stored, so the answer has no
  `warnings`.

`GET /api/v1/learnings` takes `brain_path` (AGH-393): a note under `brain/`, with or without the `brain/` prefix, at
most 512 characters. It keeps the learnings whose note is that one, in either stored form, in the list's own order
(newest proposal first) and pages; a path the note route refuses (under `auto/`, `..`, not `.md`) answers 400 naming
`brain_path`.

Problems: a `q` with no letter or digit (`!!!`, `(`) → 400 naming `q` with the reason `the query has no words`; a `q`,
`kind` or `limit` out of its bounds → 400 naming the parameter; the query is never echoed. A backlinks `path` the
brain rules refuse → 400 "Invalid brain path"; one under `auto/` → 404 "Brain note not found", as the note route
answers. An unknown project → 404. The checkout cannot be listed (no `git` on the server's `PATH`, a `git` step that
fails, or a listing over its bounds: 20,000 Markdown files, 64 MiB, 30 s per source) → 502 "Could not read the hub's
files", whose `detail` is `hub search`'s one line without its `hub search:` prefix (e.g. `git is not on PATH; install
git`); the web client does not retry it. SQLite without FTS5 → 503 "Search unavailable" with its line. The index's
database cannot be upgraded when the index is first opened (`MigrationError`) → 503 "Database upgrade failed" with
the fixed detail "The database could not be upgraded to the latest schema."; a busy or unreadable database keeps the
app's 503s ("Collector database busy", "Collector database unavailable"). The index is opened by the first knowledge
request, not at start, so the app starts on a Python without FTS5 and a failed open is tried again by the next request.
A build without the knowledge reads wired answers 501.

These routes keep the read rule of every `GET` ([Local security](#local-security)): a foreign `Origin` is served and
no CORS header is sent, so a foreign page can make the server run a sync but never read the answer. The sync is the
only write: it writes rows derived from the checkout, the same rows `hub search` writes, never the query, the kinds or
the path; with nothing changed on disk it writes nothing, so it cannot change what any route answers.

## Feature detail

`GET /api/v1/features/{project}/{slug}` serves one feature as a `FeatureDetail` (the records are in
[design/feature-records.md](design/feature-records.md)); it never calls Linear. Besides the list's fields, the
acceptance criteria rows, the records and every eval, it carries:

- `plan`: `null` without `plan.md`, else `version` (`v1` plus one per amendment entry under `## Amendments`),
  `amendments` (each `id`, `date`, `who`, `title` and `anchor`, the text of the `## Amendments…` heading) and
  `problem`. A `plan.md` over 256 KiB has `version: null` and its `problem`; the rest of the detail is served as
  usual.
- `acceptance_eval`: `null` before a whole-feature eval exists, else its `delivery` (`legacy` for `eval.md`),
  `verdict` and `owner_wait`. It is the latest eval whose scope is `acs: all`, or a legacy `eval.md` without scope.
  `owner_wait` is what a SHIP-WITH-OWNER-STEPS acceptance eval waits on from the owner, by the rule the owner
  sign-off follows (two-level-flows A9-A11, A15): `state`, `acs` (the ACs it waits on) and `reopened` (those whose
  latest eval is NO-SHIP). `state` is, in this order, `no_acs` (no live AC to sign off), `undated` (the eval has no
  usable `evaluated_at`; a legacy `eval.md` never is), `future` (dated at or after the read), `reopened`, else
  `sign_off`, the one state in which a sign-off can be recorded; with `future`, `signable_after` is the instant (UTC,
  rounded up to the minute) after which one can be. It is `null` when nothing waits, when not every eval was read
  (the sign-off's first refusal), and once an owner decision newer than the eval settled it (a "more work" still the
  latest eval of a waiting AC).
- `verdict` and `verdict_line` (here and in the list) are the acceptance eval's: a legacy `eval.md` keeps its own
  verdict line, an `evals/` record reads "Verdict: <verdict>, from the <delivery> eval". A ticket-scoped eval never
  sets them.
- `cost` (AGH-521): what the feature's sessions cost so far, estimated from their transcripts: the sessions of the
  project that touched `brain/features/<slug>/` (read or changed a file there) or worked on one of its `issues`,
  each counted once (a subagent's turns are part of its session). `total_usd` adds up the priced ones (`null` when
  none is), `sessions` counts them all and `unpriced` those without a price; with no session found, `total_usd` is
  `null` and both counts are 0.
- `phase` and `golden_path` (here, in the list and on the tickets route): the steps are the feature's own, `spec`,
  `ux_design`, `research`, `plan`, `tickets`, `build`, `acceptance`, `shipped`, and a step's `state` is one of
  `done`, `current`, `partial`, `pending`, `skipped`, `blocked`, `unknown` or `unrecorded` (Acceptance with no
  whole-feature eval); the ticket steps also use `waiting` (paused until the owner decides) and `stale` (a record to
  make again). Each step carries a `signal`, `null` or the one line that needs attention: Plan's is "v3 waits for
  you" while a plan change request is open, or the change requests' record problem (two-level-flows AC-2.8). The
  values `implement`, `review` and `evaluate` are gone (two-level-flows AC-1.1).
- `waiting_on_owner` (here and in the list): `null`, or what the feature waits on from the owner, `kind` and
  `tickets`: `change_request` while a plan change request is open (`tickets`, the origin tickets of the open
  requests), else `owner_signoff` while the acceptance eval's `owner_wait` is `sign_off`, or `owner_signoff_manual`
  while it is `no_acs` (a sign-off only the owner can write by hand, two-level-flows A17); `tickets` is empty for
  both.
- `change_requests`: the plan change requests (`change-requests/<n>.md`, two-level-flows S2) by number, each with
  `n`, its asking `ticket`, `status` (`open`, `approved` or `declined`, folded from its decision; `null` when the
  request cannot be read, `problem` then says why), `plan_from`, `plan_to`, `affected`, `opened_at`, `run_id`,
  `decision` (`null`, or `decision`, `decided_by`, `decided_at` and `note`), `path` (relative to the hub's
  `brain/`) and `approval_id`: the id of the open gate of its run that answers it (an open `human_gate` approval in
  the run's session `run:<run_id>`), `null` when the request is not open or its run has no open gate, and
  `decidable_here`: `true` for an open request whose run has no open gate and is gone by the decision route's own
  test (no `run_id`, no run folded under it, or one that ended `done`, `failed` or `cancelled`, and no child hub web
  started holds it); always `false` where the decision route is not wired (sessions off). With an `approval_id`, hub web decides through
  `POST /approvals/{approval_id}/decision` and the run writes the records; with `decidable_here`, through
  [the decision route](#plan-change-requests) below; with neither, the run is live and asks at its gate when it
  gets there (P8, A5).
- `ac_rows[].signed_off` (AGH-425): `true` when the AC does not pass in `features.json` but its latest evals are all
  the owner's SHIP (`provenance: owner`): the owner checked it by hand. It counts as passing in `acs.passing` (here
  and in the list) and is no longer counted under `acs.owner_steps`.

`POST /api/v1/features/{project}/{slug}/owner-signoff` also takes `acs` (1 to 200 AC ids, AGH-425) instead of
`delivery`: the owner signs off the criteria they checked by hand. It writes an owner eval over exactly those live
ACs, with no tickets, and answers 409, writing nothing, for an unknown or withdrawn AC, for `acs` together with
`delivery`, for `done` over an AC whose latest eval is NO-SHIP, when the note would not rank newer than an eval
naming one of them (undated, or dated at or after now), and when not every eval was read. An empty list is 422.

## Feature tickets

`GET /api/v1/features/{project}/{slug}/tickets` serves one feature's tickets, their planning and its golden path
([ADR 0025](adr/0025-reading-the-tracker-from-the-app.md); the records are in
[design/feature-records.md](design/feature-records.md)). It is the only route that may call Linear. An unknown
project or slug is a 404 and a parameter over 200 characters a 400, as for the feature detail; for a known feature it
always answers 200 with a `FeatureTickets`:

- `source`: `linear` when the ticket data comes from a Linear snapshot, `plan` when it comes from `features.json`
  only; `stale` (`true` when Linear's last good snapshot is served after a failed read, at most 15 minutes old) and
  `as_of` (when that snapshot was read; `null` with the plan).
- `notice`: why the data may be out of date, `null` for a fresh Linear read. Without a connection (no
  `LINEAR_API_KEY` where `hub web` runs, or `tracker.transport: "mcp"`, which the app never uses): "From the plan
  (features.json); Linear is not connected for hub web, so status may be stale. Set LINEAR_API_KEY where hub web
  runs." A failed read names its cause ("Linear could not be read (it timed out) …").
- `tracker_problem`: `null`, or the failed read as RFC 9457 members `type`, `title`, `status` and `detail` (redacted,
  never the key). `type` is `urn:agent-hub:problem:tracker-<kind>`, `<kind>` one of `not_connected`, `unauthorized`,
  `timeout`, `rate_limited`, `unavailable`, `unexpected`, `unreachable`, `too_many` or `other`. `status` is Linear's
  HTTP status when it answered a 4xx or 5xx; else 504 for a timeout, 502 for an answer of an unexpected shape, and
  503 for every other kind (no answer, not connected).
- `tickets`: one row per ticket (the plan's `tickets` and the record's `linear` ids), each with its `ref` (the tracker
  id, else the plan key), `key`, `id`, `title`, `state` (`name`, `type`), `assignee`, `url` (only under
  `https://linear.app/`), `priority`, `estimate`, `repo` (the plan's one repo, else `null`), `repos` (every repo the
  ticket owns, in contract and merge order), `pr_url` and `prs` (each pull request of its review record, `{repo,
  url}`, in merge order; `pr_url` is the first), `order`, the `acs` it covers, `blocked_by` edges tagged
  `plan`, `linear` or `both`, `blocks`, `readiness` (`can_start`, `waiting`, `done`, `canceled`, `in_cycle`,
  `unknown`), `waiting_on` and `reviewed`. Without Linear the statuses are `null`. Each row but an epic carries its
  `flow` (two-level-flows AC-1.8): `steps`, the seven ticket steps `context`, `preflight`, `implement`, `review`,
  `eval`, `pr` and `merged` in that order, each with a `state` (the golden path's states) and a `meta` or `null`, and
  `current`, the first step neither `done` nor `unrecorded` (`merged` when there is none), and `signal`, the ticket's
  one line that needs attention or `null` ("Waiting for you: plan change", "Held: plan change pending",
  "Plan v3 approved: re-run preflight", "Local drift · 2 notes"). How each step is read is in
  [design/feature-records.md](design/feature-records.md) "Ticket flow"; an epic's `flow` is `null`.
- `planning`: `layers` (tickets that can run in parallel, in turn), `can_start`, the recommended `order`, `waiting`,
  `cycles`, `external_blockers` (with their Linear status), `critical_path` and `warnings`.
- `golden_path`: the same steps the feature list and detail carry, recomputed with this read.

The read goes through an in-memory cache keyed by the project and the feature's ids: a snapshot younger than 60 s is
served without a call, concurrent reads of one key share one call (a read waits at most 30 s for one in flight), and any Linear failure
(401/403, 429, 5xx, timeout, unreachable, unexpected answer) holds that key for 60 s, serving the stale snapshot
(under 15 min old) or the plan. Not connected (no key, or `"mcp"`) makes no Linear call and is never held. A Refresh in
the app refetches the route; the cache still applies (`as_of` shows its age). `GET /features` and
`GET /features/{project}/{slug}` never call Linear: they use a warm cache entry, else the plan, and say so in their
`golden_path` and `tickets_source`.

## Plan change requests

- `GET /api/v1/features/{project}/{slug}/tickets/{ticket}` serves what the ticket panel shows that no tickets row
  carries (`TicketRecords`, two-level-flows A7, A20): `ticket` as asked (its plan key or tracker id, any case),
  `preflight` (`null` without `preflight.json`, else every run oldest first, each as `agent-hub/preflight/1` writes
  it with its `local_notes` and its `input`/`input_text` for a discovery or a declined change, and the `problem`
  when it cannot be read, `runs` then empty), and `change_requests`, the requests the ticket asks or is affected
  by, as the detail serves them (with `approval_id` and `decidable_here`) plus each one's `body`: its markdown after
  the frontmatter (evidence and proposal), within the 16 KiB head the reader reads, and `body_cut`, `true` when the
  file goes on past that head; the detail's `body` is `null`. It never calls Linear. A ticket the feature's `features.json` neither plans
  nor lists in `linear` is a 404.
- `POST /api/v1/features/{project}/{slug}/change-requests/{n}/decision` with `{decision, note?}` → 201 with the
  decided `ChangeRequestView`. It answers a request whose run is gone (the run abandoned, ended, or its record
  lost, AC-2.14, D-10): it creates `change-requests/<n>.decision.md` once (`type: change-request-decision`,
  `decision` `approved` or `declined`, `decided_by`, `decided_at`, `note`, each on one line; D-11), never editing the
  request, and the next `/implement` of its ticket reads it. `decided_by` is the person the project's hub commits as
  (`author_name` from `hub.json` with `hub.local.json`, else git config, as the item writes' author). It refuses,
  writing nothing: a decline without a note, 422 `urn:agent-hub:problem:change-request-note-required` (D-2); while
  the run's gate is open, 409 `change-request-gate-open` (answer it through the detail's `approval_id`); while the
  run lives (folded `running`, paused at a gate just decided or not opened yet, or held by a child hub web
  started), 409 `change-request-live-run`: the run records the decision; these two are checked, and the file
  created, holding the run commands' lock; a request
  already decided, or a decision file (or link) of that name already there, 409 `change-request-decided`; no person
  to name (none, empty or `unknown`), 409 `change-request-no-person` (A5); a request that cannot be read, 409
  `change-request-unreadable`; a folder that is a link or went away, 409 `change-request-unwritable`. Each carries
  `code`. An unknown feature or request is a 404, a body with another key or decision a 422, `n` outside 1 to 999999
  a 422. No link is followed: each folder below the hub (`brain/`, `features/`, the feature, `change-requests/`) is
  opened without following one, and the file is created exclusively there. It is a strict write that needs
  the launch cookie, as a gate's decision (`RUN_WRITES`, [Local security](#local-security)).

## Agent sessions

`hub web` starts and drives Claude Code sessions of the user's own `claude`
([ADR 0031](adr/0031-driving-claude-code-sessions-from-the-app.md); design in
[design/agent-sessions.md](design/agent-sessions.md)). Seventeen route-method pairs, all under
`/api/v1/agent-sessions`; ids are UUIDv7, a request id at most 64 characters of `[A-Za-z0-9_-]`.

| Route | Answer |
| --- | --- |
| `GET /workdirs?project=` | `{items, warnings}`: the hub, its repos and their worktrees, by opaque `workdir_id` (16 hex) |
| `GET /capabilities` | `{available, reason, engine, cli_version, models, cloud, cloud_followup}`; 200 even when unavailable |
| `GET /resumable?project=&workdir_id=` | past Claude sessions of that workdir (at most 200, newest first) |
| `GET ""` · `POST ""` | the sessions, newest first · start one: `{project, workdir_id, mode?, model?, prompt?, resume_session_id?, fork?, screenshot?}` → 201, `Location` |
| `GET /{id}` · `DELETE /{id}` | the session with its open permission request · delete an ended one with its log → 204 (409 when live) |
| `GET /{id}/events?after=&limit=` | the persisted log, `seq` order, `limit` 1 to 500 (default 200), `next_after` |
| `GET /{id}/stream` | the log over SSE (below) |
| `POST /{id}/messages` | `{text, screenshots?}` (text 1 byte to `--message-max-bytes`, 1 MiB UTF-8 by default; 1 to 10 screenshots) → 202 `{seq}`; accepted while a turn runs |
| `POST /{id}/interrupt` | `{}` → 202; the turn's `result` follows on the stream |
| `POST /{id}/permissions/{request_id}` | `{decision: allow \| deny \| always, message?, answers?, suggestion?, mode?}` → 200 |
| `POST /{id}/settings` | `{mode?, model?}` (at least one) → 200; a mode change of a session held to a tool policy (an investigation session) is 409 `mode-locked` and changes nothing |
| `POST /{id}/close` | `{}` → 200; idempotent |
| `GET /cloud` · `POST /cloud` | cloud sessions recorded here, newest first (at most 50) · `{project, workdir_id, task}`: always 501 `cloud-unavailable` with the terminal command as `guidance` (`claude --cloud` needs a terminal; no process is run) |
| `POST /cloud/{cloud_id}/messages` | `{text}`: 501 `cloud-unavailable` with `guidance` (no start is ever recorded, so a follow-up has nothing to reach; the `claude -p --cloud` path stays behind `cloud_followup`) |

- **Modes and models.** `mode` is `default`, `acceptEdits` or `plan` (never a bypass mode). `model` is `default`,
  `opus`, `sonnet`, `haiku` or an id matching `^[A-Za-z0-9._\-\[\]]{1,64}$`; anything else is 422 and the driver is
  not called. Status is `idle`, `running`, `waiting_permission`, `ended` or `failed`; without a first prompt a new
  session is `idle` with no `init` yet.
- **Workdir ids.** A `workdir_id` is the first 16 hex digits of SHA-256 over `<kind>\0<real path>` (`kind` is `hub`,
  `repo` or `worktree`). The server resolves an id only by looking it up in `GET /workdirs`; the dev client computes it
  to preselect the checkout Vite serves.
- **Screenshot.** `POST ""` may carry `screenshot: {media_type: "image/png", data: <base64>}`, sent to Claude as an
  image before the first prompt's text, in the same message. It needs `prompt` (else 422) and only `image/png` is
  accepted (else 422 "Invalid request body"). `data` must be strict base64 of a PNG (else 422 `invalid-screenshot`)
  of at most 3,932,160 bytes decoded (3.75 MiB, so its base64 fits the Anthropic API's 5 MiB image limit; else 413
  `screenshot-too-large`); every check runs before the session starts. The request body of this route alone may be
  up to 160 MiB (413 "Request body too large" above it). No image byte is stored, streamed, logged or echoed: the first
  `user.message` record's body carries a marker instead,
  `attachments: [{kind: "screenshot", media_type: "image/png", bytes: <decoded size>}]`.
- **Images in a later message.** `POST /{id}/messages` may carry `screenshots: [{media_type: "image/png", data}]`
  (1 to 10; an image pasted in the chat, converted to PNG by the browser), sent to Claude before the message's text.
  Each is checked like the first prompt's screenshot, before anything is logged or sent (422 `invalid-screenshot`
  points at `/screenshots/{index}/data`; 413 `screenshot-too-large`). This route's body may be up to 160 MiB. The
  `user.message` record carries one `attachments` marker per image and never its bytes.
- **Images and files in the first prompt.** `POST ""` may also carry `screenshots` and `files`, as a later message
  does (below), checked the same way before the session starts; like `screenshot`, they need `prompt`.
- **Files in a later message.** `POST /{id}/messages` may also carry
  `files: [{name, media_type: "application/pdf" | "text/plain", data: <base64>}]` (1 to 10, at most 5 MiB decoded
  each), sent to Claude before the images and the text: a PDF as a document block, a text file as a text block
  wrapped in `<file name="…">`. `data` must be strict base64 of a PDF (it starts with `%PDF-`) or of UTF-8 text
  without NUL bytes (else 422 `invalid-file`, pointing at `/files/{index}/data`); over the size, 413
  `file-too-large`. No file byte is stored: the record carries
  `attachments: [{kind: "file", media_type, bytes, name}]`.
- **Observed twin.** `GET ""` and `GET /{id}` carry `observed_session_id`: the `claude_session_id` once the hooks or
  transcripts observed that Claude session (it is then a row of `GET /api/v1/sessions`), else `null`, so a list shows a
  driven session once, with or without its twin. The other routes answer it `null`.
- **Permission answers.** `always` needs `suggestion`, the index of one of the request's suggestions; a request
  carries only `addRules` suggestions with behaviour `allow` and destination `localSettings` (a `setMode`,
  `addDirectories` or other suggestion is never shown, and naming one is 422); `answers`
  only for `AskUserQuestion`; `mode` (`default` or `acceptEdits`) only for plan approval, applied after the allow.
  Other combinations are 422. The first answer stands (a second is 409); none within 10 minutes is a deny by
  `timeout`.
- **Records.** Each record is `{seq, at, kind, by, body}`. Kinds: `init`, `text`, `thinking`, `tool.call` (Edit and
  Write carry a unified `diff`), `tool.result` (at most 64 KiB, then `truncated` and `original_bytes`; a file tool's result carries the
  engine's `diff` with the file's real line numbers when Claude reported one), `todos`,
  `permission.request`, `result` (cost, usage, terminal reason), `error`, `exited`, and the audit kinds
  `user.message`, `permission.decision`, `interrupt`, `settings`, `close`, `log.truncated`, `cloud.start`,
  `cloud.followup`; `by` is `web`, `timeout`, `closed`, `driver` or `server`. Stored text is redacted (the event store's rule
  set); a request's live frame and `GET /{id}`'s open request carry the raw summary (at most 4 KiB).

**Stream.** `GET /{id}/stream` sends `retry: 3000`, then the stored records after the resume position, the deltas
the ring still holds, then live frames:

- `event: record.<kind>`, `id: <seq>`, the record as data (gap-free `seq`);
- `event: delta`, `id: <seq>.<n>` (`seq` the last record, `n` the delta's place in the open text block), data
  `{after_seq, block, index, text}`; deltas are never stored, and the completed `text` record supersedes them;
- `event: status` (no id), `{status, end_reason}` when the session's state changes; `event: heartbeat` every 15 s
  with the last id sent; `event: reset` (no id) `{reason}` when the position cannot be resumed (malformed, unknown or
  another session's): the client reloads from `GET /{id}`. A delta position whose block left the ring resumes with
  that block's completed `text` record instead.

`Last-Event-ID` (or `?after=`, the header wins) is `<seq>` or `<seq>.<n>`, at most 32 characters. Frames sent live
carry the original text; a replay carries the stored, redacted copy. An unknown session is a 404 problem before any
byte; an ended session's stream replays its log and ends.

**Access.** Every route of the family needs the cookie `agent_hub_<port>`, reads included: `hub web` mints a token
per launch and prints `/?token=<token>`; a `GET` or `HEAD` of a page with `token` answers 303 to the same address
without it and, when it matches, sets the cookie (`HttpOnly; SameSite=Strict; Path=/`). No cookie or a wrong one is
401 `urn:agent-hub:problem:agent-session-unauthorized`. Writes also need the server's own `Origin`,
`Sec-Fetch-Site: same-origin` when sent, and a JSON body except on `DELETE` (403, 415); a bodiless command sends
`{}`. Reads, the stream included, refuse any other `Origin` and a `Sec-Fetch-Site` of `same-site` or `cross-site`
(another loopback port is same-site and would carry the Strict cookie) and accept a missing `Origin` with a valid
cookie: Chromium sends none on a same-origin `EventSource` (verified); Firefox and WebKit are unverified. With
`AGENT_HUB_IN_CONTAINER=1` every route answers 404 `urn:agent-hub:problem:agent-sessions-off` and no token is
minted. No route speaks WebSocket: any upgrade is closed with code 1008. Under `make dev`, open the token address
`hub web` printed (port 7420) once: cookies are not port-scoped, so the dev server's `/api` proxy then carries it.

Every driven session starts, and reopens, without the credential names its hub declares (`credentials.env` names
and an `AWS_PROFILE` naming a declared `aws_profile`, AM-13). While those names cannot be read, creating or
reopening a session answers 409 and nothing starts (E-8): `urn:agent-hub:problem:hub-local-invalid`
(`code: hub_local_invalid`, the detail names `hub.local.json`) when the hub's `hub.local.json` cannot be read, and
`urn:agent-hub:problem:hub-registry-unreadable` (`code: hub_registry_unreadable`, the detail names the registry) when
the hub registry cannot be read.

**Problems** (`urn:agent-hub:problem:agent-session-<code>`; details name ids, limits and causes, never conversation
text or a value the browser sent):

| Code | Status | When |
| --- | --- | --- |
| `not-found` · `unknown-request` | 404 | no such session · no pending request with that id (`request_id`) |
| `terminal` | 409 | the session ended or failed (`session_status`); resume it |
| `busy` | 409 | a command while an interrupted turn ends, or deleting a live session |
| `answered` | 409 | a second answer to a request |
| `log-full` | 409 | the log reached 50,000 records or 32 MiB; the session ended (`end_reason: log_full`); resume it |
| `limit` | 429 | a fifth live session (`limit`) |
| `invalid-workdir` · `unknown-resume` · `invalid-decision` | 422 | an id not in `GET /workdirs` or `GET /resumable` (`errors[]`) · an answer that does not fit the request |
| `message-too-large` | 413 | a prompt or message over the limit (`limit`, `size`) |
| `screenshot-too-large` | 413 | a screenshot over 3,932,160 bytes decoded (`limit`, `size`) |
| `invalid-screenshot` | 422 | a screenshot that is not strict base64 of a PNG (`errors[]` points at `/screenshot/data`, or `/screenshots/{index}/data` for a message's image) |
| `file-too-large` | 413 | a message's file over 5,242,880 bytes decoded (`limit`, `size`) |
| `invalid-file` | 422 | a message's file that is not strict base64 of a PDF or of UTF-8 text (`errors[]` points at `/files/{index}/data`) |
| `unavailable` | 503 | no `claude` on `PATH` or no `sessions` extra (`reason`), on every write |
| `restriction-unavailable` | 409 | a message to an ended session that cannot be reopened safely (E-13): a scenario investigation session whose tool policy cannot be rebuilt from its run, any session while the hub's scenario runs (or a link file in them) cannot be read to tell whether it is one, or any session whose project no registered hub names (for example, the project was unregistered between two registry reads) (`detail` says which) |
| `mode-locked` | 409 | a permission-mode change of a session held to a tool policy (a scenario investigation session, E-15): its mode stays `default`, so the writes and `./hub` commands its policy allows keep asking; a model change still applies. Such a session reads `restricted: true` (the member is absent for other sessions) |
| `cloud-unavailable` · `cloud-failed` · `cloud-timeout` | 501 · 502 · 504 | link-out guidance (`guidance`) · the step that failed (`step`) · the 60 s deadline (`seconds`) |

## Skills

Three GET routes (and the two version history reads below) serve a hub's skills, agents and hooks, read from its
files on request (the hub tree under `plugin/` and `.claude/`, through `HubFileReader.skill_sources` and
`read_skill_file`, never through a link). The GETs never write the hub (the restore and the publish below do); the
catalog, the detail and the version list
record a version of each unit they show in agent-hub's database (`item_versions`, AGH-295: a baseline the first time,
a new version when its content changed; never a unit with a secret match or past the bounds), and a capture that
cannot write within the database's busy timeout answers 503.
Other methods answer 405; no route runs a script, a hook or a command.

- `GET /api/v1/projects/{project}/skills` → `SkillCatalog`: `items` (each with `id` `kind/source/name`, `kind`,
  `source`, `name`, one-line `description`, `origin`, `mode`, `invocation`, hub-relative `source_path`,
  `diagnostics_count`, `usage` over the last `usage_days` (30; `null` for hooks), `linked_from`, and for hooks `active`
  and `state`), `external_plugins` (name, marketplace, pin, enabled, `content: "not in this hub"`), `truncated` and
  `notice`. A hub with no skills answers 200 with no items and the notice "No skills found in this hub; it may not be
  synced yet."
- `GET /api/v1/projects/{project}/skills/{kind}/{source}/{name}` → `SkillDetail`: the catalog fields plus the
  header fields (`description_full`, `when_to_use`, `argument_hint`, `allowed_tools`, `tools`, `model`, `lock`),
  ordered `frontmatter` pairs with `known`, `body`, `raw` (the file as UTF-8), `toc`, the derived `structure`, `uses`,
  `used_by`, bundled `files` (id, path, role, size, `link`, `too_large`), `diagnostics`, `context_cost` (approximate)
  and, for a hook, `hook` (event, matcher, type, command, timeout, active, state).
- `GET /api/v1/projects/{project}/skills/{kind}/{source}/{name}/files/{file_id}` → `BundledFileText`: id, path,
  role, size and `text`, or `binary: true` and no text for a file with a NUL or that is not UTF-8.
- `GET /api/v1/skill-usage[?project=…&days=7|30|90]` → `UsageReport` (AGH-482): `days` (default 30), `items` and
  `truncated`. One row per skill or agent in each scoped hub's `.claude/skills` and `.claude/agents` (a real entry, or
  a plugin item a link there points at), each `{project, kind, name, runs_7d, runs_30d, runs_90d, last_used_at}`
  (names, counts and a time only, ADR 0019; 0 runs and `null` when unused in 90 days). Rows never run in `days` come
  first, then by runs descending, then project, kind and name. Not paginated (the catalog's bounds cap it); `days`
  outside 7, 30 or 90 → 400; a scope naming no registered project answers no items. `truncated` is `true` when the
  catalog was cut or a file was not read, or the usage fold kept only 500 names. It records no item version.
- `GET /api/v1/projects/{project}/skills/{kind}/{source}/{name}/versions[?limit=…&cursor=…]` → `ItemVersionPage`:
  the versions of the item's unit (a skill's folder, an agent's file, a hook's whole file) newest first, `limit` 1 to
  200 (default 50) with a cursor ([Pagination](#pagination)), each `{id, origin, first, author, recorded_at,
  content_hash, size, restored_from, draft_id}` (`author` `{name, email}`, `null` for `external`); plus `next_cursor`,
  `total_estimate`, `state` (`ok`, `too_large`, `secret` or `unreadable`: what the disk holds now), `managed` (per
  `hub.lock`), `unit_path`, `unit_kind` and `shared_by` (the items the unit holds: every hook of one file lists the
  same versions). The list captures its unit first (as the detail does, sharing its memo), so a changed unit shows
  its new version; a unit past the bounds or with a secret match keeps its earlier versions listed.
- `GET /api/v1/projects/{project}/skills/{kind}/{source}/{name}/versions/{version_id}` → `ItemVersionContent`: `id`,
  `unit_kind` and `files` (`path`, `executable`, `size`, and `text`, `null` for a binary file); a file unit has one
  file named after it. Only a version of the item's own unit is served.
- `POST /api/v1/projects/{project}/skills/{kind}/{source}/{name}/versions/{version_id}/restore` with
  `{confirm_managed?}` → 200 `ItemWriteResult` `{changed, versioned, reason, version}`: writes the version back into
  the hub (a skill's folder is made equal to it, its files' executable bits and all, files and now-empty folders the
  version does not hold removed, the folder's hidden entries kept; a hook's whole file, so every hook in it) and
  records a `restore` version naming it in `restored_from`, by the hub's effective identity (`author`). One write runs
  at a time in the server. Before it writes, the disk's content is recorded as an `external` version when it differs
  from the last one, so a hand edit stays restorable. A version equal to the disk answers `changed: false` and writes
  and records nothing; content with a secret match or past the bounds is written with `versioned: false` and its
  `reason` (`secret`, `too_large`). A strict write that needs the launch cookie ([Local security](#local-security));
  its refusals are listed under [Errors](#errors). It spawns no process (no git, and the project is resolved from
  the registry and `hub.json` without the hub card's doctor drift check): the hub's working tree shows the change.
- `POST /api/v1/projects/{project}/skills/drafts/{draft_id}/publish` with `{target, confirm_managed?}` → 200
  `ItemWriteResult` `{changed, versioned, reason, version}`: lands the Studio's draft `.hub-drafts/<draft_id>/` in the
  hub (D10, S5) and records a `publish` version naming the draft (`draft_id`), by the hub's effective identity.
  `target` is `{kind, source, name}` (the catalog id of the item the draft edits) or `null` for a new item, always
  stated; `confirm_managed` is as for a restore. An edit of a skill writes every draft file over its counterpart and
  keeps the files the draft does not hold (a changed `name` publishes to the new folder, carries the old folder's
  hidden entries, records the new unit's `publish`, then removes the old folder); an agent's file is replaced (a
  changed name: the new file, the old removed); a hook's draft groups replace that one hook in its file, every other
  hook and setting kept, the file written in the `dump_json` form. A new item lands in the project's own plugin,
  `plugin/<project>/` (`skills/<name>/`, `agents/<name>.md`, or merged hook by hook into `hooks/hooks.json`, created
  when missing, a new hook's `scripts/*` copied to `plugin/<project>/scripts/`). It goes through the restore's write
  step (one write at a time, the disk recorded first as `external`, the same gates); then the draft is removed, also
  when the draft equals the item (`changed: false`, nothing written or recorded). A written unit with a secret match
  or past the bounds answers `versioned: false` with its `reason` (`secret`, `too_large`), and a write of a new hook's
  scripts only `reason: "script_only"`. A draft some version of the project already names as its `publish` is spent
  (409 `draft_already_published`). Claude only edits the draft; the server reads it here, never through a link. Like
  the restore, it spawns no process (no git, no doctor drift check), also when the draft just changed the tree.

Items and files are addressed by ids the server issues (`file_id` is 16 hex characters of the sha256 of the file's
hub-relative path), never by a client path. Bounds: 500 items per kind, 200 bundled files per skill, 2,000 hooks,
256 KiB per file, 16 MiB read per catalog; past one, `truncated` is `true` with a notice and an over-cap file carries
the diagnostic `too_large`.

## Workflows

Two GET routes serve the registered hubs' workflows, read from their files on request through the generator's
discovery (the hub's `workflows/<pack>/` files, then the built-ins; a hub workflow overrides a built-in of its name).
They never write the hub; the list and the detail record a version of each hub workflow file they show in agent-hub's
database (`item_versions`, AGH-295, as for the Skills routes; never a built-in or a pack's other files), and answer
503 when that capture cannot write within the database's busy timeout. A hub's read is reused while its listing
fingerprint (path, size and mtime of each entry of its `workflows/` and the built-ins, stat only) is unchanged. A problem never names an absolute path.

- `GET /api/v1/workflows[?project=…]` → `WorkflowCatalogView`: `items` (each with `project`, `name`, `description`,
  `revision`, `source` `hub` or `builtin`, `node_count`, `layer_count`), by project then name, and `problems` (each
  with `project`, hub-relative `file` (a built-in's starts `<builtin>/`), `line` or `null`, `key` (`$` for the whole
  file) and `message`), one per file that does not load or plan. A project scope that names no project is empty.
- `GET /api/v1/workflows/{project}/{name}` → `WorkflowDetail`: the summary fields, `layers` (in run order, each a list
  of nodes `{id, type, depends_on, description}` in declaration order), `document` (the file's content as written,
  keys left out not filled in) and `environment`, the one a process workflow declares (`null` without one). An unknown project is a 404 (entity `project`); an unknown workflow, or one listed as a
  problem, is a 404 (entity `workflow`, id `<project>/<name>`). A parameter over 200 characters is a 400. The routes
  answer 501 only in a build where the workflow reads are not wired.
- `GET /api/v1/workflows/{project}/{name}/versions[?limit=…&cursor=…]` and `.../versions/{version_id}` → a hub
  workflow file's `ItemVersionPage` and one version's `ItemVersionContent`, as for the [Skills](#skills) routes
  (`unit_kind` `workflow`, `shared_by` 1). A built-in has no history (404, entity `item history`).
- `POST /api/v1/workflows/{project}/{name}/versions/{version_id}/restore` with `{confirm_managed?}` → 200
  `ItemWriteResult`: writes the version back into the hub workflow's file, the pack's other files left as they are,
  as the [Skills](#skills) restore does (the same gates and problems).

## Workflow run commands

Four POST routes start and stop workflow engine runs (AC-213.19, ADR 0032 decision 4). Each runs the hub that serves
the web as a child (`python -I -m agent_hub.cli workflow run …`, argv only, in the hub folder), with the server's
environment minus `LINEAR_API_KEY`, plus `AGENT_HUB_ROOT` and `AGENT_HUB_DB` (the server's store, absolute), so the
run's events, written by the child through `IngestEvents`, are the ones `GET /workflow-runs` folds. The routes track
no status: it comes from those events.

- `POST /api/v1/workflow-runs` with `{project, workflow, inputs}` → 202 `RunAccepted` (`run_id`, `project`,
  `action`) and `Location: /api/v1/workflow-runs/{run_id}`. A web start is always live (`--live`); a dry run belongs
  to the CLI (`hub workflow run NAME` without `--live`), and a `live` member is refused like any unknown one (422).
  The run id is minted first (8 hex digits, the CLI's pattern). `inputs` (at most 64, names `^[a-z][a-z0-9_]*$`,
  strings up to 16,384 characters without NUL, finite numbers, booleans, at most 262,144 bytes in all as
  `name=value` argv text) must fit the workflow's `inputs` (422 `workflow-run-invalid-inputs`). `issue-to-pr` is refused (409 `workflow-run-tracker-workflow`): its tracker writes
  need `LINEAR_API_KEY`, which no child gets; use `hub run`.
- **One live run per issue.** A run's issue is its `issue` input when the workflow declares one and the value is a
  tracker key (`^[A-Z][A-Z0-9]{0,9}-[0-9]{1,9}$`); only then do its events carry `issue`. A run folded `running`, or
  a child the server started that has not ended, refuses another start or resume of that issue (409
  `workflow-run-live-run`, with `run_id`). A start and a resume take one lock from that check through the launch.
- `POST /api/v1/workflow-runs/{run_id}/cancel` → 202: SIGINT to the child's process group (the CLI kills its node
  children), SIGKILL after 10 s, then `--abandon`, so the run ends `cancelled` (a failed abandon is logged). Only a
  child this server started is signalled: while the server holds it unreaped, or, after a restart, while its process
  still has the start time its pid file records (`/proc` on Linux, else `ps`); otherwise 409
  `workflow-run-not-running`.
- `POST /api/v1/workflow-runs/{run_id}/resume` → 202 (a detached `--resume` child) and
  `POST /api/v1/workflow-runs/{run_id}/abandon` → 200 (waits for `--abandon`, at most 60 s). Both refuse a run that
  ended `done` or `cancelled` (409 `workflow-run-ended`), whose child still runs or whose run lock another
  `hub workflow run` holds (409 `workflow-run-in-use`), or that is not an engine run (409
  `workflow-run-not-engine-run`); the CLI refusing is 409 `workflow-run-refused`. Of two concurrent launches of one run,
  one answers 409 `workflow-run-in-use`. At most 8 children started from the web run at once (409
  `workflow-run-too-many-runs`). A child that cannot start or finish is 502 `workflow-run-launch-failed`. Problems
  never quote the CLI's output.

A started child runs in its own session with stdin empty and both streams appended to
`<hub>/.agent-runs/web/<run>.log`; its pid file `<hub>/.agent-runs/web/<run>.pid` (pid, start time, issue) is created
exclusively, owner-only, never through a link, locked by its writer until its record is written, and removed
when the child ends. A file still locked by its writer (another `hub web` mid-launch) answers 409
`workflow-run-in-use`; a folder named `<run>.pid` is skipped. A pid file whose process is gone or
started at another time is removed when the folder is next read (at most 64 files, start times read outside the
launcher's lock within a 2 s budget); one whose start time cannot be read in time is kept, counted live and never
signalled. A file that changes or is taken by a new child while it is judged is kept and counted live, and a launch
whose pid file reads otherwise than when it was judged (an empty file just made included) answers 409
`workflow-run-in-use`. A `.agent-runs/web` that is a link is refused (502). `run_id` in a path
must match `^[a-z0-9][a-z0-9-]{0,31}$` (else 400). All four are strict writes ([Local security](#local-security)) and
need the launch cookie, like the agent-session writes; with `AGENT_HUB_IN_CONTAINER=1` they answer 404
`urn:agent-hub:problem:run-control-off`.

## Workflow gate decisions

A paused engine run's `approval` or attention `wait` is an open `human_gate` approval whose id is its `gate_id`
(`<run>:<node>:<attempt>`, session `run:<run>`). Two routes answer it from the web (AC-213.18, AGH-231):

- `GET /api/v1/approvals/{approval_id}/gate` → `WorkflowGate`: `run_id`, `project`, `workflow`, `node`, `attempt`,
  `form` (`decision` for an approval, `choice` for a wait with `options`, `text` for one without), `choices`
  (`{id, label}` from the node's `decisions` or `options`, the defaults Approve and Reject included) and `text`:
  `off` (an approval without `capture_response`), `optional` (an approval with it, or a wait with options) or
  `required` (a wait without options). They come from the workflow's current definition, as the run graph's do; the
  run's record has the final word on the decision. An approval that is no gate a person answers in an engine run's
  workflow is 409 `workflow-run-not-workflow-gate` (another kind, another session, a timed wait or a node the
  workflow no longer has: `workflow-run-gate-not-in-workflow`), a decided one 409 `workflow-run-decided`.
- `POST /api/v1/approvals/{approval_id}/decision` with `{decision?, text?}` → 202 `GateDecided` (`approval_id`,
  `run_id`, `project`, `decision`) and `Location: /api/v1/approvals/{approval_id}`. `decision` is a declared
  decision or option id (`^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 characters); `text` has no NUL and at most 65,536
  bytes in UTF-8. An answer the gate cannot take is 422 `workflow-run-invalid-inputs` (no decision or an undeclared
  one, an option for a text wait, a blank text where one is required, a text where `text` is `off`). Under the run
  commands' lock the run is refused as a resume would be (409 `workflow-run-ended`, `-in-use`, `-live-run`). Then the
  server runs `hub workflow decide <run> --gate <gate_id> [--choice <id>] [--text-stdin]` and waits for it (at
  most 60 s): the CLI's `DecideGate` records the decision in the run's record under its lock and sends a
  `control_plane` `gate.result` (where `web`), and the text goes on the child's stdin, never in argv. The CLI
  refusing (the gate closed or was decided meanwhile, the run in use) is 409 `workflow-run-refused` and nothing
  resumes; otherwise the run resumes in a detached child as `POST /workflow-runs/{run_id}/resume` does. A
  `hub workflow decide` that cannot start answers 502 `workflow-run-launch-failed` (nothing recorded); one that
  outlasts the 60 s answers 502 `workflow-run-decision-unknown`, since it may have recorded the decision before it
  was stopped (the approval, or a resume, tells). A resume that cannot start answers 502
  `workflow-run-resume-failed` with the decision kept: resume the run to continue.

The decision is a strict write that needs the launch cookie, like the run commands; with `AGENT_HUB_IN_CONTAINER=1`
it answers 404 `urn:agent-hub:problem:run-control-off`.

`GET /api/v1/approvals` names an open gate's kind when its run's own record does (`gate_kind`: `policy` for a policy
ask, `investigation` for a scenario run's investigation; each run's record read once per request, never through a
link), never from the gate's id (E-10); an authored gate, another kind or a record that cannot be read has no
`gate_kind` member. `GET /api/v1/workflow-runs/{run_id}` adds `environment` when the run's own start record names one
(`{name, access, production}`, the access and production flag from the hub's effective config as read now, both
`null` when it cannot be read or no longer declares it); hub web's best-effort banner reads it. Without one the member
is absent.

## Scenarios

The hubs' scenarios and their scenario runs ([design](design/scenarios.md), AGH-350 plan T12, AC-350.21, .22, .23,
.30). A scenario run is a WorkflowRun labelled `scenario:<name>`: `GET /api/v1/workflow-runs?kind=scenario|workflow`
keeps one kind (absent: both, as before; `WorkflowRun.kind` says which), and its events and gates are a run's.
The reads need no cookie but for a run's values; every `POST` below is a strict write ([Local
security](#local-security)) that needs the launch cookie and, as that values read, answers 404
`urn:agent-hub:problem:run-control-off` in the container, except the builder's save, dismiss and action writes and a
migrate, which answer 409 `hub_read_only` there. The CLI does the work as a child, as for the [run
commands](#workflow-run-commands) (`python -I -m agent_hub.cli …`, argv only, in the hub folder, the server's
environment minus `LINEAR_API_KEY`); no problem quotes its output.

- `GET /api/v1/scenarios[?project=…]` → `ScenarioCatalogView`: `items` (each `project`, `name`, `pack`, `description`,
  `revision`, `node_count`, `inputs` and `last_run`: `{run_id, status, started_at, ended_at, environment, mode}` of
  its newest scenario run, or `null`; `environment` and `mode` come from the run's start record, `null` when it cannot
  be read), by project then name, and `problems` (as [Workflows](#workflows)' list: a file of `scenarios/`
  that does not load or plan). Read from the files on each request through the generator's discovery.
- `GET /api/v1/scenarios/{project}/{name}` → `ScenarioDetail`: the summary, `steps` in declaration order (`id`,
  `type`, `action` for an `action` or `expect` step, `depends_on`, `description`), `runs`, its scenario runs,
  newest first (at most 50, each as `last_run`), and `environments`, the project's declared environments to plan in
  (`name`, `access`, `production`, from `hub.json` tightened by `hub.local.json`; empty when either cannot be read). An unknown project is a 404 (entity `project`); an unknown scenario, or one listed as a
  problem, a 404 (entity `scenario`, id `<project>/<name>`).
  Each step also carries its keys (AGH-521): `with`, `capture`, `every`, `timeout`, `until_when` and `retry`
  (`max_attempts`, `delay`, `on_error`). The detail adds `path` (the scenario file, relative to the hub),
  `document_text` (its YAML), `document` (the file as JSON, read with the strict loader: the builder's starting
  point), `content_hash` (`sha256:` of the file's bytes, the `base_content_hash` a save sends) and `actions`, one per action the steps call: `ref`, `name`, `pack`, `path`,
  `description`, `effect`, `runtime`, `script`, `timeout`, `inputs` (`name`, `type`, `required`, `default`,
  `description`), `output_format`, `draft` with its `accept_command`, `document_text`, `script_text` (cut with
  `script_truncated`) and `problem` when the action does not load.
- The scenario builder (AGH-521, hub web's editor of a scenario; `SCENARIO_PATHS` lists its seven paths):
  - `POST /api/v1/projects/{project}/scenarios/validate` with `{pack, document}` → 200 `ValidateResult`: `loads`,
    `yaml` (the canonical YAML Save would write, `generator`'s scenario writer), `problems` (`error` or `warning`,
    each on its `node` or the document) and `nodes` (each top-level node's first and last line in `yaml`). It writes
    nothing. The document is a `version: 1` graph or a `version: 2` tree (AGH-507): a tree's action references are
    checked through its translated blocks, each problem on the block's first node with the block's key path
    (`stages[0].steps[2].do`).
  - `GET /api/v1/projects/{project}/actions` → 200 `ActionLibrary`: the hub's actions, by pack then name, each with
    its `output_fields` (the paths a reference may read, two levels) and `used_by` (the scenarios that call it, a
    tree's Do and Wait until blocks included), and the `problems` of action files that do not load.
  - `PUT /api/v1/scenarios/{project}/{name}` with `{pack, document, base_content_hash}` → 200 `SaveResult` (`path`,
    `revision`, `content_hash`, `yaml`, `changed`, `versioned`): writes `scenarios/<pack>/<name>.yaml` through the
    item write step (recorded as a version, never through a link, no git command), only when the document loads (409
    `document_invalid` else) and only over the file the builder last read (409 `stale_document`; `null` for a new
    scenario, 409 `name_taken` when another pack holds the name). The server sets `revision` (the file's plus one);
    a document whose canonical bytes with the file's own `revision` equal the file's writes nothing and keeps the
    revision (`changed: false`), a graph or a tree alike.
  - `DELETE /api/v1/scenarios/{project}/{name}` → 204 removes the scenario's file and Claude's proposal for it from
    the hub folder (never through a link, 409 `link_in_path`; not while its newest scenario run is in progress or
    waits for you, 409 `scenario_run_in_progress`; no git command, so the file comes back only from the
    hub's git history); its recorded scenario runs stay. 404 (`about:blank`) when no scenario of that name loads, so
    a second DELETE answers 404. A DELETE sends no body, so it needs no JSON content type (no 415); its Origin is
    checked as any strict write's (403), it needs the launch cookie (401), and in the container it answers 409
    `hub_read_only`.
  - `GET /api/v1/scenarios/{project}/{name}/proposal` → 200 `ProposalView`: the document Claude wrote for the scenario
    under the hub's ignored `.agent-runs/`, checked as Save would check it; 404 when there is none. `POST
    …/proposal/dismiss` → 204 removes it once the owner accepted it into the draft or rejected it (never through a
    link).
  - `POST /api/v1/projects/{project}/actions` with `NewAction` (`pack`, `name`, `description`, `effect`, `runtime`
    `python` or `sh`, `timeout`, `inputs`, `outputs`, `script_text`) → 201 `ScenarioActionView`: writes the action's
    document and its script as a draft (409 `name_taken`, `document_invalid`); it runs and commits nothing. `PUT
    /api/v1/projects/{project}/actions/{pack}/{name}` rewrites an action of the hub the same way (409
    `unknown_action`); the action is a draft until it is committed again.
  - The save, the delete, the dismiss and the two action writes are item writes (`ITEM_WRITES`): strict Origin rules and the
    launch cookie, and 409 `hub_read_only` in the container ([Local security](#local-security)).
- `POST /api/v1/scenarios/{project}/{name}/plan` with `{environment, inputs?}` → 200 `ScenarioPlanView`: what `hub
  scenario plan NAME --env ENV --json` prints (`scenario`, `environment`, `access` (`null` when undeclared),
  `production`, `denied`, `problems` and `rows`, each `step`, `type`, `action`, `effect`, `args` (a value known only
  at run time as `<$CTX.<name> from <node>>`), `endpoints` (input → `{service, url, resource}`), `every`, `timeout`,
  `content_hash`, `draft`, `decision`, `reason_kind`, `reason` and `plan`: the script's plan-mode summary, called
  with no credential and only when every arg is known (AM-8)), plus, per row, `needs_acceptance` (a draft action) and
  `accept_command`, the exact `git add -- … && git commit -m …` line that accepts it (AM-5: nothing commits from
  hub web). The inputs (as a run's: at most 64, names `^[a-z][a-z0-9_]*$`) are checked against the scenario's first
  (422 `workflow-run-invalid-inputs`), and a `hub.local.json` that cannot be read or conflicts with `hub.json` is 409
  `hub-local-invalid` before any child runs, as for a start; the child runs in its own session, its stdout read in chunks up to 4
  MiB and its stderr dropped; past 300 s or that cap its process group gets SIGINT (the CLI then kills its
  plan-mode scripts' groups), SIGKILL 5 s later, and the call answers 502 `workflow-run-launch-failed`.
- `POST /api/v1/scenarios/{project}/{name}/runs` with `{environment, inputs?, mode?}` (`interactive`, the default,
  or `regression`) → 202 `RunAccepted` (`action` `start`) and `Location: /api/v1/scenario-runs/{run_id}`. The
  scenario is planned first (core's `plan_scenario`, the config as read now); a plan that may not start creates no
  run and answers 409 with `code` and every problem and denied step in `detail`: `undeclared_environment`, `denied`
  (with `steps`, the denied steps' ids, and each step's reason) or `plan_problem` (an action or endpoint that cannot
  be resolved, a path an action's output lacks, two unordered gates). Then `hub scenario run NAME --env ENV --mode
  MODE --run-id RUN` starts detached, which plans and refuses again on its own.
- `GET /api/v1/scenario-runs/{run_id}` → `ScenarioRunDetail`, read from the run's record in a registered hub's
  `.agent-runs/workflows/<run_id>/records.jsonl` (never through a link, at most 8 MiB, a torn last line dropped):
  `scenario`, `pack`, `environment`, `mode`, `status` (the end's, `null` while it has none), `open_investigation`
  and `paused_step` (the investigation waiting for an answer), `timeline` (each line's `event`, `node`, `attempt`,
  `status`, `at`, and an investigation read's (`agent_action`) `action` and `effect`), `polls` (an expect's polls:
  `held`, never the output; outputs only through `…/values`, below), `captures` (`name`, `value`), `decisions` (every gate's answer: `choice`, `text`,
  `approver`, `where`), `actions` (each action call's policy facts: `node`, `attempt`, `poll`, `action`, `effect`,
  `origin`, `decision`, `reason_kind`, `content_hash`, `approver`, `status`, `failure_kind`, `at`; never its inputs
  or output, which only `…/values` gives), `findings`, `investigations` (each with `agent_session_id`, the session its
  `investigation-<n>.session` link names, read never through a link, else `null`), `workarounds` and `proposal`: the latest investigation's latest proposal, each option with its `steps`, its
  `plan` as shown, `needs_acceptance`, `accept_commands` (one per drafted action that is still a draft),
  `pickable` and `refusal`, judged now as an answer would be (only while its investigation waits; `the
  investigation is answered` after). A run no registered hub holds, or one that is not a scenario run, is a 404.
- `POST /api/v1/scenario-runs/{run_id}/investigation` → 201 `InvestigationSession` (`run_id`, `project`,
  `investigation` (its number), `step`, `agent_session_id`, `started: true`) and `Location:
  /api/v1/agent-sessions/{agent_session_id}`; a later call for the same investigation answers 200 with the same
  session (`started: false`). The run must be a scenario run paused at an open, unanswered investigation, as its own
  record says. The session starts in the hub, mode `default`, with the investigation's system prompt, its tool
  policy (a `PreToolUse` hook: `Read`, `Glob`, `Grep` only inside the hub and its declared repos and never on a
  declared env file, under `/proc` or on `/`, and no `Grep` with a `glob` filter under a folder holding a declared env
  file; `Write` under `actions/<pack>/`; Bash for the listed `./hub` commands only; every other tool denied) and,
  like every driven session, without the credential names the hub declares; no env file is read here. The link file
  `investigation-<n>.session` in the run folder, created exclusively and owner-only, keeps it to one session per
  investigation and per `hub web` process. A link that is empty (a start cut short), names a session the store does
  not know, or names one that ended and cannot be resumed is taken over by a new session (an error listing what can
  be resumed is answered, never taken as "cannot be resumed"); a start that fails removes the link; a link that
  cannot be written stops the session it would have named.
- The chat is the agent-session routes' (`POST /api/v1/agent-sessions/{agent_session_id}/messages`, AM-9). A message
  that reopens an ended investigation session (after a restart, for example) rebuilds its tool policy and prompt from
  the link and the run's record, or is refused (409 `agent-session-restriction-unavailable`). Its permission mode cannot change (409 `agent-session-mode-locked`).
- `POST /api/v1/scenario-runs/{run_id}/answer` with `{choice, option?}` (`pick` with an option id `o<n>`, `retry` or
  `stop`; an option without a pick, or a pick without one, is 422) → 202 `InvestigationAnswered` (`run_id`,
  `project`, `investigation`, `step`, `choice`, `option`) and `Location: /api/v1/scenario-runs/{run_id}`. The
  investigation must be open and unanswered (409 `workflow-run-not-paused`). A pick is checked first, as `hub
  workflow respond` checks it (core's `pick_problem`): an option of the latest proposal that holds no `deny`, no
  draft action and whose plan is still the one shown; else 409 `workflow-run-pick-refused` with the reason in
  `detail`, and nothing is recorded. Then, under the run commands' lock (409 `workflow-run-in-use` while the run's
  child runs), `hub workflow decide <run> --gate <run>:<step>__investigation:<n> --choice <choice> [--text-stdin]`
  records it, as for a [gate decision](#workflow-gate-decisions) (the same 409 `workflow-run-refused` and 502s), and
  the run resumes in a detached child: `stop` ends it `cancelled` with its findings kept, `retry` runs the step
  again, `pick` runs the workaround, then the step. Approvals sends an investigation gate here (409
  `workflow-run-investigation-gate` there).
- `POST /api/v1/scenario-runs/{run_id}/findings/{finding_id}/issue` with `{confirm?}` → 200 `FindingIssue`: the
  draft `hub scenario findings --issue` prints (`title`, `description`) and the `team` it goes to (`hub.json`'s
  `tracker.team`, or the first of `tracker.teams`; `null` when `hub.json` cannot be read), `created: null`; the draft
  never reads `hub.local.json`. With `confirm: true` (the terminal's `y`; only the JSON `true` confirms, anything else
  is 422) the tracker is resolved from the effective config, `hub.json` with `hub.local.json` over it (a local
  `tracker.transport` wins; a `hub.local.json` that cannot be read or conflicts with `hub.json` is 409
  `hub-local-invalid`), then its `create_issue` is called once and the answer is 201 with `created: {id, url}`.
  The marker `finding-<id>.issue` in the run folder, shared with `hub scenario findings --issue`, is claimed
  exclusively before the call and then holds the issue or the failure; the claimer holds `flock` on
  `finding-<id>.issue.lock` from the claim until the result is recorded, so a running create is never retaken (409
  `workflow-run-issue-exists`, "a create of finding <id>'s issue is running"; held with no marker yet, "busy …; try
  again"), and a crash releases it. A created issue answers `recorded: true`; one whose marker could not be written
  answers 201 with `recorded: false` and a `warning` ("the issue <id> was created but could not be recorded: …; do
  not create it again"). A marker naming an issue refuses every later
  create on both sides (409 `workflow-run-issue-exists`, naming it). A create the tracker refuses or does not answer
  is 502 `urn:agent-hub:problem:scenario-run-issue-failed`; that marker, or the empty one a crash leaves, is also 409
  `workflow-run-issue-exists` here (the issue may exist), and only a terminal retries it: `hub scenario findings
  --issue` shows the state, warns that the issue may already exist in the tracker and asks again. Without a tracker
  key (transport `api`), 409 `workflow-run-tracker-not-connected`; transport `mcp` reaches Linear through `claude -p`
  in the hub, as the CLI does.
- `POST /api/v1/scenario-runs/{run_id}/findings/{finding_id}/inbox` → 201 `FindingNote` (`path`, hub-relative):
  writes `brain/_inbox/<date>-scenario-<name>-<finding>.md` (`provenance: agent-from-external`, the CLI's text),
  never over an existing note (409 `workflow-run-note-exists`) nor through a link (409 `workflow-run-link-in-path`).
  `finding_id` matches `^f[0-9]{1,6}$` (else 400); an unknown finding is a 404 (entity `finding`).

Debugging and migration (AGH-507, [ADR 0049](adr/0049-scenario-blocks-and-run-control.md), [design](design/scenarios.md)
§ Debugging): the debug writes run the CLI as a child, as a gate decision does, and are run writes (`RUN_WRITES`);
migrate runs in the server, as the builder's Save does, and is an item write (`ITEM_WRITES`); the values read needs the
same cookie ([Local security](#local-security)). A block address in a body must fit the address grammar
(`^[1-9][0-9]*(\.((then|else|p[1-9][0-9]*)\.)?[1-9][0-9]*)*$`, at most 64 characters; else 422 for the body), so none
reads as an option of the CLI, which gets them after `--` (or as `--break=ADDR`).

- `PUT /api/v1/scenario-runs/{run_id}/breakpoints` with `{blocks: [<address>…]}` (at most 512 addresses of the run's
  pinned tree, as [design](design/scenarios.md) § Tree format writes them) → 200 `Breakpoints` (`run_id`, `blocks`, in
  the pinned tree's declaration order, each once): replaces the run's breakpoints through `hub scenario break RUN --set
  -- ADDR…`, waited for (at most 60 s); one set while the run runs takes effect at its next layer of nodes, so the
  run's child may be running. An address the pinned tree (the run snapshot's document, read up to 1 MiB and never
  through a link, not the scenario file as it reads now) does not hold, any address of a version-1 run included, is 422
  `workflow-run-unknown-block` naming it (`block`); its `detail` says when the snapshot cannot be read (missing, a
  link, over 1 MiB or no longer a tree) rather than that the run is a version-1 one; a run that ended `done` or
  `cancelled` is 409 `workflow-run-ended`. An empty list clears them, also on production. The CLI refusing after these
  checks (another command changing the run's breakpoints, a version-1 run asked to clear) is 409
  `workflow-run-refused`; one that cannot start or finish in time, 502 `workflow-run-launch-failed`.
- `POST /api/v1/scenario-runs/{run_id}/step` and `…/continue` → 202 `RunAccepted` (`action` `step` or `continue`) and
  `Location: /api/v1/scenario-runs/{run_id}`: the run must be in a debug pause, as its record says (409
  `workflow-run-not-debug-paused`; a gate keeps its own paths), its `debug.pause` line must read back (422
  `record_unreadable`) and its child must have ended (409 `workflow-run-in-use`); then `hub scenario step|continue RUN`
  runs detached, as a resume does: it records the command with the approver (the account `hub web` runs as) and
  resumes the run, or refuses on its own (a snapshot that no longer matches its `content_hash`) and records nothing.
- `POST /api/v1/scenarios/{project}/{name}/runs` also takes `breakpoints` (as above, addresses of the tree the run
  pins, the scenario's file as read now; 422 `workflow-run-unknown-block` else, a version-1 scenario included), passed
  as one `--break=ADDR` each. Its plan's problems name a block, `block <address> (<key path>)`, as the CLI's do, and a
  required input that neither the body nor the environment's values fill is 422 naming the input and the environment,
  for a plan as well.
- When the run's environment is `production: true` in the effective config as read then, breakpoints other than an
  empty list, Step, Continue, a start with breakpoints and a values read are 409 `workflow-run-debug-production` and
  nothing is recorded; a start without breakpoints is unchanged.
- `ScenarioRunDetail` adds `debug` (`null` unless the run is in a debug pause: `block`, `node`, `reason` `breakpoint`
  or `step`, `number`, `at`), `breakpoints` (the addresses last set), `stepping` (whether its last debug command was
  a Step) and `blocks`, the blocks of the tree the run pins (`address`, `kind`, `label`, in declaration order, read
  from its snapshot as breakpoints are checked, not from the scenario file as it reads now; empty for a version-1 run
  or a snapshot that cannot be read), and each `timeline` line its `block`: the address of the pinned tree's block
  that holds its node, as the values read gives it (a gate's is its step's, an included node's its include's; `null`
  in a version-1 run and on a line about no node): metadata only, as the rest of it. `ScenarioDetail` adds `version`
  (`1` or `2`) and, for version 2, `blocks` (`address`, `kind`, `label`, `entry_nodes`) in declaration order, read
  from the file as it reads now; `entry_nodes` are the translated graph's, while a run starts a gated step at its
  `<step>__ask` gate and an include at the first nodes of what it includes, so a run's lines are put on blocks by
  their `block`.
- `GET /api/v1/scenario-runs/{run_id}/values` → 200 `ScenarioRunValues`: `run_id`, `inputs` (the run's effective
  inputs, environment values included) and `blocks`, one per finished node in the order they first ended (`address`
  of the block that holds it: a gate's is its step's, an included node's its include's, `null` in a version-1 run;
  `node`, `attempt`, `status`, `with` as rendered, `output`,
  and for a Wait until `polls` and `last_poll`), from the record (values as it holds them, credential values already
  redacted). It needs the launch cookie and this server's pages (a foreign `Origin` or a `same-site` fetch is 403), as
  the agent-session routes do, so no other local process reads it; the run must be paused, its last pass ended on a
  pause (a debug pause or a gate) or waiting for an investigation's answer (409 `workflow-run-not-paused`), and its
  environment not production (409 `workflow-run-debug-production`). In the container, where no cookie exists, it is
  404 `run-control-off`.
- `POST /api/v1/scenarios/{project}/{name}/migrate` with `{check?, base_content_hash?}` → 200 `ScenarioMigration`
  (`path`, `written`, `yaml` (the tree, canonical; `null` with problems), `content_hash` (the file's after the call)
  and `problems` (`node`, `message`)): what `hub scenario migrate NAME [--check]` does, in the server: core's
  `migrate_graph` over the bytes it read once, `generator`'s canonical writer, the text loaded back and translated
  again, then the item write step Save uses (recorded as a version, never through a link, no git command). With
  problems (a node a tree cannot hold, a JSON file, a link, a path the writer does not write) nothing is written
  (200, `written: false`, `node` `null` for the file's own); with `check` nothing is either. When `base_content_hash`
  is sent, the file must still hold it (409 `stale_document`), so a builder Save between a check and the write is never
  overwritten: the bytes are read first (never through a link), so a JSON file or a path the writer does not write is
  checked too and, unchanged, answers its problem; a link is never read, so its problem is the answer whatever hash is
  sent. A version-2 scenario is 409 `scenario_already_tree`; in the container it is 409 `hub_read_only`.

## Local security

`hub web` binds `127.0.0.1` only. It refuses a `Host` header other than `127.0.0.1:<port>`, `localhost:<port>` or
`[::1]:<port>` (403, against DNS rebinding), a path holding a control character once decoded (404 "Not Found", before
any other check: the router's `$` also matches before a trailing newline, so `…/values%0A` would reach the route
while the checks below, which match the whole path, would not apply) and a `POST` or `DELETE` whose `Origin` is not
its own (403); it sends no
CORS headers, `Cache-Control: no-store` on `/api`, and a CSP that limits scripts, styles, fonts and connections to
`'self'`. The web app requests no other host; Linear is read by the server only ([Feature tickets](#feature-tickets)).
A `GET` with a foreign `Origin` is served, the knowledge `GET`s included: their only write is the sync of derived
index rows, which a foreign page can trigger but whose answer it cannot read ([Knowledge](#knowledge), AGH-393 AM-2).
The agent-session routes add a cookie and stricter Origin rules ([Agent sessions](#agent-sessions)), and the workflow
run writes (`RUN_WRITES`: start, cancel, resume and abandon a run, a gate's decision, an AC's check run, a
change request's decision, and the scenario writes: a plan, a start, an investigation's session and answer, a
finding's issue and inbox note; and, with AGH-507, a run's breakpoints, Step and Continue), the restores,
the Publish, the scenario builder's save, proposal dismiss and action writes (AGH-521), a scenario's migrate
(AGH-507) and its delete (AGH-596) (`ITEM_WRITES`) need that cookie too, as does the read of a scenario run's values
(`RUN_READS`, with the agent-session reads' Origin rules) ([Workflow run commands](#workflow-run-commands), [Skills](#skills),
[Workflows](#workflows)); every other route is unchanged and needs no cookie. In the container (`AGENT_HUB_IN_CONTAINER=1`, where no token is
minted and the hubs are mounted read-only) a restore, a publish or a scenario builder write (a migrate and a delete
included) answers 409 `hub_read_only` before the cookie is checked, and a run write or the values read 404 `run-control-off`.

The two learning decisions, which reach the network, the four workflow run commands and a workflow gate's decision,
which start or stop processes, and the two restores and the Publish (`ITEM_WRITES`), which write into a hub's tree,
take a strict rule
on top (`STRICT_WRITES` in `agent_hub/api/local_security.py`), checked before the route runs, so a refused request
pushes, stores, writes and starts nothing:

- `Origin` is required and must equal `http://<Host>`, the server's own origin (403 "Forbidden origin" when absent or
  different);
- `Sec-Fetch-Site`, when the browser sends it, must be `same-origin` (403 "Forbidden fetch site");
- `Content-Type` must be `application/json`, parameters aside (415 "Unsupported media type"). A cross-site form cannot
  send that type without a CORS preflight, which the server never grants.

The other writes keep the checks above only. `make dev`'s Vite proxy rewrites its own `Origin` to the API's and drops
any other, so the dev server passes the strict rule and stays CSRF-safe.
